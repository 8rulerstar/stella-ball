## 1. 이미 되는 것 (실측)

- **모션 축소를 존중한다.** `prefers-reduced-motion: reduce`를 켜면
  실행 중인 CSS 애니메이션이 **0**이 된다(스타일시트 다섯 곳에 규칙이
  있고 스크립트도 `RM` 분기를 쓴다).
- **메타 화면은 탭으로 돈다.** 타이틀에서 `관측 시작 → 1분 튜토리얼 →
인트로 다시 보기` 순환이 정상이고, 허브·상점·소환·프로필의 조작은
  전부 실제 `<button>`이라 키보드로 닿는다.
- **상태는 소리로 읽힌다.** (2026-08-23 재확인 — 아래 정정 참고.) `#tip`은
  `aria-live="polite"`이고 **실제로 보인다**: `prism-breakers-interface.css:510`
  이 `display: none`으로 끄지만 `stella-ball-upgrade.css:77`이
  `display: block !important`로 되살린다(같은 파일 :95가 `.tip:empty`만 다시
  숨긴다). 실기 확인(계산 스타일과 내용):
  허브 `display:block` · 「파티를 편성하세요.」,
  전투 `display:block` · 「메사르팀 · 세 점의 고리 · 노드를 셋 찍어…」.
  즉 조준 안내가 가는 라이브 리전은 살아 있고 낭독된다.

  > **정정(2026-08-23).** 이 항목은 2026-08-22에 한 번 「틀린 기록이었다 —
  > `#tip`은 display:none이라 한 번도 울리지 않는다」로 뒤집혔는데, **그
  > 뒤집기가 틀렸다.** 당시 `prism-breakers-interface.css`의 `display: none`
  > 까지만 보고 「그 뒤 어떤 시트도 되살리지 않는다」고 단정했으나,
  > 마지막 스타일시트가 `!important`로 되살리고 있었다. 계산 스타일을
  > 직접 읽었으면 바로 나왔을 값이다 — 소스만 읽고 캐스케이드를 추론한
  > 것이 원인이다. 지금 문장이 실측 결과다.

  `#toast`에 `aria-live`가 없는 것은 그대로다.

## 2. 이번에 고친 것

전투 캔버스에 `role="img"`와 설명을 붙였다. 지금까지는 **이름 없는
그림**이라 스크린리더가 「여기에 무엇이 있는지」조차 말하지 못했다.
상태 중계는 위의 `#tip`이 이미 하므로, 캔버스는 「무엇을 보고 있는가」만
말하고 나머지는 그쪽에 맡긴다.

## 3. 결정된 것 — 전투를 키보드로 할 수 있게 했다 (2026-08-22)

**결정 전 상태는 이랬다.** 실측:

| 화면                         | 탭으로 닿는 조작       |
| ---------------------------- | ---------------------- |
| 타이틀·허브·상점·소환·프로필 | 전부                   |
| **전투**                     | **일시정지 버튼 하나** |

노드 조준은 좌클릭으로 노드를 찍고 빈 곳을 눌러 반대편을 고른다 —
**전부 포인터 전용**이다. `Space`는 발사만 하므로, 키보드만 쓰는
플레이어는 판을 볼 수는 있어도 한 발도 쏠 수 없다.

이것은 버그가 아니라 **조작 규칙의 공백**이라 코드로 밀지 않았다.

### 무엇을 넣었나

오너 결정: 「전투 키보드로도 할 수 있게해」(2026-08-22). 마우스 경로는
그대로 두고 키보드를 **덧붙였다** — 두 손이 같은 함수로 내려가게 했다.

| 키              | 하는 일               | 마우스에서 같은 것 |
| --------------- | --------------------- | ------------------ |
| ← → (↑ ↓ · A D) | 노드 사이로 커서 이동 | 마우스 호버        |
| Enter           | 찍기 · 무르기         | 좌클릭             |
| F               | 반대편 고르기         | 빈 곳 클릭         |
| Backspace       | 전부 무르기           | 우클릭             |
| Space           | 발사                  | (원래 키보드)      |

노드가 셋 미만인 판에서는 마우스가 «드래그»로 떨어진다. **캠페인 1-1이
별지기 둘이라 실제로 만나는 판이다.** 키보드도 같은 자리에서 같은 손을
갖는다 — ← →로 겨누고, ↑ ↓로 세기를 정하고, Space로 놓는다. 안내선은
드래그의 것을 그대로 쓰고 발사도 드래그와 «같은 계산»(cuePull)을 지나므로,
보이는 선과 나가는 곳이 어긋나지 않는다.

- 커서가 없을 때의 첫 Enter 는 «커서를 세우는» 동작이다. 어디를 찍을지
  들려주고 나서 찍게 하려는 것이다.
- 초점이 «판»에 있으면 Enter 는 조준의 것, «버튼»에 있으면 버튼의 것이다.
  그래야 키보드로 판을 멈출 수도 있다. 화살표·F·Backspace 는 버튼에서
  하는 일이 없으므로 어디서든 조준이 가져간다.
- 마우스를 움직이거나 누르면 키보드 커서를 놓아 준다 — 링이 두 곳에 뜨지
  않는다. 넘겨줄 때 낭독도 갱신한다.
- 판이 탭 순서에 있는 것은 전투 화면에서만이다. 그대로 두면 허브·상점에서
  보이지 않는 캔버스가 첫 탭 자리를 차지한다.
- 판을 탭 순서에 넣고 이름표에 키를 적었다. 화면에는 글자를 더하지
  않았다(판 위 한글은 창에 따라 5.4px 까지 줄어든다 — BOARD_TEXT).
- 화면 밖으로 잘라 낸 라이브 리전(`#aimLive`)을 따로 만들어 조준 상태를
  낭독한다. `#tip`을 그대로 두고 따로 만든 이유 — §1의 정정 뒤로도 이
  선택은 유효하다. `#tip`은 «판 밖의 안내 문구»를 담는 자리이고
  (「파티를 편성하세요.」 · 스테이지 소개), 조준은 매 픽마다 바뀌는
  «순간 상태»다. 한 리전에 둘을 섞으면 안내가 조준 낭독에 계속 밀린다.

### 수업 1단계의 잠김도 풀었다

1-1 수업 1단계는 파티를 일부러 비워 둔다(별지기가 서면 노드가 셋이 되어
좌클릭이 «찍기»로 넘어가고, 그 단계가 가르치는 드래그가 도달 불가능해진다).
그 대가로 **키보드만 쓰는 사람은 발사 경로가 드래그 하나뿐이라 1단계에서
영영 못 나갔다** — 노드가 0개면 `aimStarReady()`가 거짓이라 Space 가
`launchAimStarShot` 에서 즉시 되돌아간다. 노드가 하나도 없는 판에서만
도는 키보드 발사(`launchKeyboardPull`)를 주어 풀었다. 방향은 그 단계의
훅이 어차피 보스로 덮어쓰므로 정할 것이 없다.

### 검증

마우스 이벤트를 한 번도 쓰지 않는 프로브 둘로 확인했다.

```bash
node scripts/probe-keyboard-battle.mjs      # 캠페인 전투를 키로만
node scripts/probe-keyboard-onboarding.mjs  # 수업 전체를 탭·엔터·키로만
```

- 초점 계약 양방향: 판에 초점이면 Enter 가 «찍고 안 멈추며», 버튼에
  초점이면 Enter 가 «멈추고 안 찍는다».
- 노드 둘인 판: 화살표로 겨누고(271도 · 세기 77%) Space 로 나간다.
- 캠페인: 커서 이동 · 셋 찍기 · 반대편 왕복 · 전부 무르기 · 발사 · 보스
  처치 · 승리 화면까지. 콘솔 오류 0.
- 수업: 타이틀 → 1단계 → 2단계 → 3단계 → 실전에서 보스 처치 → 업적 해금.
  콘솔 오류 0.
- 마우스 쪽 온보딩 E2E(`npm run check`)는 그대로 통과한다.
