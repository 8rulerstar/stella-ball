# 수업 첫 버튼을 두 번 두드리면 게임이 대신 쏜다 — 고치려다 두 번 깨뜨린 기록

2026-08-23 출시 준비 스윕에서 확정한 입력 결함이다. **고치려고 두 번
시도했고 두 번 다 수업을 깨뜨려서 되돌렸다.** 다음 사람이 같은 벽을 다시
치지 않도록 증상·원인·실패한 두 해법을 남긴다.

## 1. 증상 — 실측

수업 1/6 의 「유성 발사하기」를 45ms 간격으로 두 번 두드리면:

|             | 유성   | 움직임 | 수업            |
| ----------- | ------ | ------ | --------------- |
| 두드리기 전 | 99     | 아니오 | phase 0         |
| 두드린 뒤   | **98** | **예** | `bossHit: true` |

플레이어는 드래그를 **한 번도 하지 않았는데** 유성이 나가고, phase 0 의
조준 보정이 그것을 거상으로 몰아 수업이 「직격! 잘했어요」로 스스로
통과한다. 첫 수업이 가르치려던 동작을 플레이어가 못 배운 채 넘어간다.

**진행 손실은 없다** — 그 판은 유성이 99개고 화면도 깨지지 않는다.
그래서 «치명»은 아니지만, 모든 새 플레이어가 누르는 첫 버튼이다.

## 2. 원인

덮개(수업 카드)가 그 클릭 «안에서» 사라지므로 둘째 타가 곧바로 판에
떨어진다. 판에서 한 번의 클릭은 누름+뗌이고, 뗌 지점이 유성에서 멀어
끄는 거리 검사(`l < 18`)를 통과해 **발사**가 된다.

캠페인에서는 안 난다 — 노드 조준이 클릭을 먼저 가져가기 때문이다.
수업 phase 0 은 파티를 일부러 비워 노드가 0개라 드래그 경로가 살아 있다.

`game-combat.js`의 `billiardPointerDown`이 입장 연출에 대해 **이미 같은
수법**을 쓰고 있다 — 「건너뛴 입력은 여기서 삼킨다」. 그 자리에 하나를
더 얹는 것이 자연스러운 방향이다.

## 3. 실패한 해법 둘 — 그리고 왜 실패했는지

### 시도 1. 시간만으로 막기 (덮개가 걷힌 뒤 260ms 동안 판 입력 삼키기)

더블탭은 막혔다. 그런데 **온보딩 E2E 가 깨졌다** —
`dragShot` 이 2초 안에 발사되지 않는다. E2E(와 실제 플레이어)는 카드를
누른 «직후» 유성을 끌기 때문에, 정상 드래그의 첫 누름까지 삼켰다.

### 시도 2. 자리까지 보기 (사라진 버튼의 상자 ±24px 안의 누름만 삼키기)

드래그는 통과했다. 그런데 이번엔 **`pickNodes` 가 3개 중 2개만 찍혔다** —
노드 하나가 하필 그 버튼 자리 근처에 있어 그 픽이 먹혔다.

### 쓸 수 없는 것

`pointerdown`의 `detail`(클릭 횟수)로 둘째 타를 가르려 했으나 **실측
결과 항상 0**이다(단발·더블 모두). 마우스 이벤트와 달리 포인터 이벤트는
클릭 횟수를 싣지 않는다.

## 4. 다음 사람에게 권하는 방향

시간·자리 어느 쪽으로 좁혀도 「방금 누른 자리 근처를 곧바로 다시
누르는」 정상 조작과 구별되지 않는다. 판 쪽에서 «막는» 대신 **덮개 쪽에서
«늦게 걷는»** 편이 맞아 보인다:

- 카드를 지울 때 같은 자리에 투명한 방패를 200~250ms 남긴다. 둘째 타는
  방패가 먹고, 판은 아무것도 안 바꾼다. 정상 드래그는 유성 위에서
  시작하므로 방패 밖이다.
- 또는 실습 버튼을 `pointerup` 이 아니라 `click` 으로 받고, 그 뒤 한 틱
  동안 `pointer-events: none` 을 카드 자리에 남긴다.

어느 쪽이든 **반드시 `npm run test:onboarding` 으로 확인할 것.**
합성 드래그 프로브는 이 검증에 쓸 수 없다 — 손으로 만든 드래그는
수정 «전»에도 발사되지 않아서, 과잉 수정을 못 잡는다(이 문서의 시도 1을
그 프로브로 통과시켰다가 E2E 에서 걸렸다).

## 6. 해결 — 2026-08-24

4절이 권한 방향(덮개 쪽 방패)은 절반만 맞았다. **뿌리는 판 쪽에 있었고 그것은
수업과 아무 상관이 없었다.**

### 6-1. 뿌리 — 「탭」과 「드래그」를 가른 적이 없다

`billiardPointerUp` 은 «유성에서 뗌 지점까지의 거리»(`l`)만 봤다.

```js
l = Math.hypot(ball.x - p.x, ball.y - p.y);
if (l < 18) {
  toast("유성을 더 멀리 끌어 당겨보세요.");
  return;
}
fireMeteor(dx, dy, force);
```

`l` 은 **손이 한 발짝도 안 움직여도** 커진다. 유성에서 먼 곳을 한 번 톡 치면
그대로 발사였다. 수업 카드가 사라진 자리에 떨어진 둘째 타가 정확히 그것이다.

이 저장소는 같은 문제를 조준 쪽에서 이미 겪고 답을 냈다 —
`billiardPointerDown` 주석의 「탭과 획의 경계가 계속 문제였고(**탭이 곧 발사가
됐다**)」가 훑기를 버리고 찍기로 간 이유다. 드래그 경로에만 그 경계가 남아
있었다.

고친 것: 누른 지점을 따로 들고(`drag.fromX/fromY`) 손이 12px 이상 움직였을
때만 발사한다. 12px 은 손떨림(0~2px) 위, 가장 짧은 의도적 끌기 아래다. 방향과
세기는 그대로 뗌 지점이 정한다 — 바뀌는 것은 「탭은 발사가 아니다」 하나다.

**`drag` 는 누른 지점이 아니었다.** `billiardPointerMove` 가 매 프레임
`drag.x/y` 를 현재 포인터로 덮는다(미리보기가 그 값을 쓴다). 첫 시도에서 그걸
모르고 `drag.x/y` 로 이동거리를 재서 항상 0 이 나왔고, **E2E 가 앞선 두 번과
똑같은 자리에서 떨어졌다**(`meteor launch timed out`). 그래서 `fromX/fromY` 를
따로 둔다.

### 6-2. 남은 절반 — 조준

뿌리 수정은 «발사»만 막는다. 카드가 걷힌 뒤 판이 조준 화면이면 둘째 타는
발사가 아니라 **조준**을 건드린다 — 노드를 찍거나 겨누는 방향을 뒤집는다.
실측으로 그 자리는 수업 두 곳이다:

| 단계    | 별지기 | 노드 | `aimStarReady` | 둘째 타가 하는 일         |
| ------- | -----: | ---: | -------------- | ------------------------- |
| phase 0 |      1 |    1 | false          | 드래그 경로(6-1에서 막힘) |
| phase 1 |      3 |    3 | **true**       | **조준이 바뀐다**         |
| phase 2 |      3 |   10 | **true**       | **조준이 바뀐다**         |
| phase 3 |      3 |    9 | false          | 첫 발 자유조준            |

그래서 4절의 방패를 함께 둔다 — 버튼이 있던 자리에 투명한 방패를 240ms.
`game-onboarding.js` 의 `shieldLessonTap`. 판 쪽에서 막으려던 두 시도가 실패한
이유가 여기에 있다: 시간만 보면 정상 드래그의 첫 누름까지 먹고, 자리까지 봐도
정상 노드 픽이 먹힌다. 덮개 쪽에서 늦게 걷으면 둘 다 피한다.

정상 조작을 먹지 않는 근거(1280×900, phase 0 실측): 버튼 448~852 · 284~331,
유성 화면 좌표 (650, 681) — 카드 아래변에서 **338px** 아래다. 다음 카드의
버튼도 안전하다: `revealDelay` 가 최소 620ms 라 방패가 걷힌 뒤에 눌린다.

### 6-3. 검증

새 프로브 `scripts/probe-lesson-double-tap.mjs` — CDP Input 으로 **진짜 마우스**
누름·뗌을 두 번 보낸다. `shieldLessonTap` 을 빈 함수로 덮어 「고치지 않으면
재현된다」까지 같은 실행에서 보여 준다.

| 간격  | 수정 전             | 수정 후           |
| ----- | ------------------- | ----------------- |
| 20ms  | 유성 99→98 · 움직임 | 99→99 · 안 움직임 |
| 45ms  | 99→98 · 움직임      | 99→99             |
| 100ms | 99→98 · 움직임      | 99→99             |
| 220ms | 99→98 · 움직임      | 99→99             |
| 300ms | 99→98 · 움직임      | 99→99             |
| 450ms | 99→98 · 움직임      | 99→99             |
| 900ms | 99→98 · 움직임      | 99→99             |

**방패만으로는 240ms 밖에서 다시 쐈다**(300ms·450ms 에서 실측). 뿌리를 고친
뒤에야 간격과 무관해졌다. 과잉 수정은 이 프로브가 못 잡으므로
`npm run test:onboarding` 으로 판정한다 — 4절의 경고대로다.

### 6-4. 곁에서 나온 결함 하나

`billiardPointerMove` 의 미리보기 위력이 **220** 으로 나누는데 실제 발사는
`cueForce` 의 **130** 을 썼다(2026-08-24 에 「판 안에서 100% 가 되게」 나눗수를
낮추면서 이쪽을 같이 고치지 않았다). 그 옆의 주석이 「미리보기도 발사와 같은
식이어야 한다 — 다르면 표시된 위력이 거짓말이 된다」인데 실제로 거짓말을 하고
있었다. 실측으로 **최대 41% 낮게** 표시했다:

| 끈 거리 | 게이지 표시 | 실제 발사 |
| ------: | ----------: | --------: |
|    60px |        0.28 |     0.462 |
|    90px |       0.409 |     0.692 |
|   130px |       0.591 |     1.000 |

식을 두 벌 두지 않고 `cueForce` 하나를 부르게 고쳤다.
